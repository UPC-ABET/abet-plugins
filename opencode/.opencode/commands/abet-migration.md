# Write a migration

The database is **in production**. That single fact drives every rule here: a migration
that has already run cannot be changed, and a migration that sorts into the wrong place
breaks every fresh environment.

The backend has two datasources. Know which one you are targeting before you start:

| Datasource | Config | Scripts |
| ---------- | ------ | ------- |
| Main | `backend/src/database/typeorm.config.ts` | `migration:create` / `:run` / `:revert` / `:generate` |
| Raw | `backend/src/database/typeorm.raw.config.ts` | `migration:raw:create` / `:raw:run` / `:raw:revert` / `:raw:generate` |

Run every script below as `pnpm --filter ./backend <script>` from the repo root, or plain
`pnpm <script>` from inside `backend/`.

The raw datasource holds scraped Banner / uPlanner data. If your change is about
application entities, it is the main one.

## Steps

### 1. Create the file with the CLI. Always.

```bash
pnpm --filter ./backend migration:create src/database/migrations/<kebab-case-name>
```

This stamps the filename with `Date.now()`, which guarantees it sorts **after** every
existing migration.

**Never hand-write the filename and never pick a timestamp yourself.** A round-number or
hand-picked timestamp drifts out of order and can run before its dependencies — a table
created before its schema exists — which breaks a fresh database while looking fine on
yours, because yours already ran the earlier ones.

`pnpm --filter ./backend migration:generate` also stamps correctly, but prefer
hand-written `up()`/`down()` per the next rule.

### 2. Write up() and down() by hand

Autogenerated SQL diffs entities against a live connection and will happily produce
destructive statements you did not intend — dropping and recreating a column instead of
altering it, or reordering constraints.

Use `migration:generate` output as a **draft to read**, then write the real thing.

`down()` is not optional and is not decorative. Write it so it actually reverses `up()`,
and say in the runbook if reversal is lossy (a dropped column's data does not come back
because `down()` re-adds the column).

### 3. Never touch an applied migration

Do not edit `1700000000000-initial-migration.ts` or anything already run. Its row exists
in the `migrations` table, so the edit will never execute against production — you will
have changed fresh environments and not production, and the two will silently diverge.

Every schema change is a **new, forward-only** migration. No exceptions.

### 4. Name constraints explicitly

Uppercase prefix, human-readable, never the auto-generated hash form
(`PK_4689ce4c54254910a1e7ab56b1c`):

| Kind | Pattern |
| ---- | ------- |
| Index | `IDX_<table>_<columns>` |
| Foreign key | `FK_<table>_<column>` |
| Unique | `UQ_<table>_<columns>` |
| Primary key | `PK_<table>` |

Hash names make a later migration that needs to drop the constraint unwritable without
querying the database first.

### 5. Think about the table while it is locked

Before running anything against a real environment, answer:

- **How big is this table?** An `ALTER TABLE ... ADD COLUMN` with a non-null default, or
  a plain `CREATE INDEX`, takes a lock. On a large table that is downtime.
  Use `CREATE INDEX CONCURRENTLY` where the change allows it.
- **Is there a backfill?** Backfilling in the same migration as the schema change ties
  them into one long transaction. Usually the right shape is: migration adds the column
  nullable → separate batched backfill (documented in the runbook) → later migration adds
  the constraint.
- **Is it reversible?** If not, the runbook must say so explicitly.

### 6. Test it both ways

```bash
pnpm --filter ./backend migration:run
pnpm --filter ./backend migration:revert
pnpm --filter ./backend migration:run
```

Up, down, up. If `down()` fails or leaves a different schema than you started with, it is
wrong — and you will only find out at the worst possible moment.

Then run the suite: `pnpm --filter ./backend test`.

### 7. Record it in the runbook

Every migration puts its deploy step in `openspec/changes/<slug>/runbook.md`, under the
deploy prerequisite section, with the exact command and its ordering relative to the
deploy. If a seed must run after it (`pnpm --filter ./backend seed:auth-roles-permissions`
after a permission change, for instance), that goes there too.

A migration that only exists in the diff and not in the runbook is a migration someone
will forget to run.

### 8. Report and stop

Show the migration file, the up/down/up result, and the runbook entry. **Do not commit,
and do not run it against anything but your local database.**
